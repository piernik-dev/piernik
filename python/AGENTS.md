# The `setup` script

## Overview
`./setup` is a symlink to `python/piernik_setup.py` (helper: `python/DirWalk.py`). It must be run
from the repository root. It does **not** compile anything by itself (unless `-n` is absent, then it
finally calls `make -j<ncpu> -C obj_<name>`). Its job is to assemble a build directory
`obj[_<suffix>]/` (option `-o`/`--obj`) and a run directory `runs/<problem>[_<suffix>]/`.

Typical use: `./setup sedov -c h5pfc_gnu` (problem name = directory in `problems/`, possibly nested,
e.g. `mcrtest/mcrtest_new`), `-n` skips compilation, `--copy` copies files instead of symlinking,
`-d FLAG1,FLAG2` adds `-D` preprocessor symbols, `-p file` selects a parameter file,
`-v` prints verbose diagnostics (the cpp command and all symbols found), `--problems`/`-u` list problems/units.
Compiler settings come from `compilers/<name>.in` (default `default.in`; a local `.setuprc` or `.setuprc.$HOSTNAME` may prepend options such as `-c camk`, so the "Using compiler settings" line may differ between machines).
The last invocation is pickled in `.lastsetup` (`--last` repeats it); the call is saved in `obj/.setup.call`.

## What it does (in order)
1. Parses options, picks `problems/<name>/`, deletes and recreates the object directory.
2. Collects all `src/**/*.F90` (`.f90`, case-insensitive) and `*.h` files, plus files from the problem
   directory and its parent directories (a file in the subproblem hides one with the same basename
   from the parent; `Makefile.in` is NOT inherited). Required: `piernik.def`, `initproblem.F90`, the
   parameter file (`problem.par` by default).
3. **Determines the set of defined preprocessor symbols** (`our_defs`) by running `cpp -dM` on
   `#include "src/base/piernik.h"` with `-D` flags from `-d` and `-I<dir of piernik.def>`. Symbols
   come from `piernik.def` (`#define ...`) and `piernik.h`.
4. Handles the `overrides` directive: a problem file may replace a file from `src/` of the same basename.
5. Source files may contain a comment `! pulled by SYM`, `! pulled by A && B`, `! pulled by A || B`;
   such a file is built only if the condition holds for `our_defs`. No comment = always built.
6. For each selected file, runs `cpp` on it (with `-D__INTEL_COMPILER`, so `use` of Intel-only
   modules is visible) and scans the result for `use` / `module` statements and `#include "..."`
   to build module dependencies.
7. Links/copies the files into the object dir, writes `Makefile` (= `compilers/<c>.in` + problem
   `Makefile.in` + `head_block1/2` templates embedded in the script + dependency lines) and
   `dep.dot` (module dependency graph, `make dep` renders it).
8. Optionally runs make, then prepares the run directory (copies/symlinks `problem.par`, `piernik`).
`version.F90` and `os_detect.F90` are generated by the generated Makefile, not by setup.

## Portability rules for calling `cpp` (macOS lesson)
- The compiler-driver `cpp` is not the same everywhere: on macOS `cpp` is clang-based and
  refuses to guess the language of `*.f90` / `*.F90` files (error `cc: error: no input files` or
  "linker input file unused"). GNU cpp (Linux, Homebrew `cpp-14`) is happy with them.
- Currently both `cpp` calls use `get_stdout()` with shell command strings; there is no `run_cpp()` helper.
  Macro discovery uses a temporary `.f90` file, and neither invocation selects the input language explicitly.
  `get_stdout()` discards stderr and does not check the subprocess return code.
- Explicit language selection that preserves Fortran syntax, avoiding temporary files, and checked subprocess
  execution with useful diagnostics are proposed portability improvements, not implemented behaviour.
- Do not rely on `$CPP` or on a specific `cpp` version. Do not assume GNU-specific flags
  (e.g. `-traditional-cpp` behaves differently on clang).
- If a user reports problems, ask for: `cpp --version`, `which cpp`, and the output of
  `./setup <problem> -n -v` (it prints the exact cpp command and the symbols found).
- The generated Makefile also uses `gcc -dM -E - </dev/null` (os_detect) and `pkg-config` (fftw3,
  fortrancl); these are other potential portability points.

## Known pitfalls / things to keep in mind
- `cpp_junk` regexp filters out `#define _...` lines (compiler internals); only symbol names are used.
  Empty macro output is not validated and raises `IndexError` while constructing `our_defs`; an explicit diagnostic is still needed.
- Lists must not be modified while iterated (this was a bug in the file-lock and `overrides` loops).
- Python sets are used for dependencies, so the order of items in the generated `Makefile` may vary
  between runs (set `PYTHONHASHSEED=0` and compare sorted lines when diffing Makefiles).
- `os.symlink` of two files with the same basename from different directories raises; this is the
  "duplicate link or name clash" message (usually a missing `overrides` directive).
- Makefile templates contain tabs and `\\`/`$$` escapes in Python strings; edit with care.
- The generated Makefile runs tiny compile tests from `compilers/tests/` (MPI f08, F2018, ...)
  to define `-DMPIF08`, `-DNO_F2018`, ...; setup itself only checks `-DMPIF08` in the `-d` flags.
- Debug leftovers (printing `cmd`/`cmdout`) were removed; use `-v` for diagnostics.

## Testing changes to setup
- Quick: `./setup sedov -n -o tmp` and `./setup maclaurin -n -o tmp`, then compare the `Makefile`
  with one generated by the previous version (`PYTHONHASHSEED=0`, compare sorted lines, ignore the
  first line that holds the setup call). Remove `obj_tmp` and `runs/*_tmp` afterwards.
- Style: `make pycodestyle` (part of QA; long lines are ignored).
- Formal test suite: `make CI -j` = `QA` (chk_err_msg, chk_lic_hdr, pycodestyle, qa) + `artifacts`
  (setup+build of various problems: dep, py3, noHDF5, I64, IOv2, Jeans, Maclaurin, 3body, CPAW)
  + `gold` (regression comparisons: CRESP, mcrtest, mcrwind, MHD sedov AMR, resist, streaming
  instability, custom). Every one of them goes through `./setup`, so a setup bug breaks everything.
- Problems from `problems/` often used as standard tests: `sedov`, `maclaurin`, `jeans`, `otvortex`,
  `crtest`, `mcrtest`, `3body_orig`, `streaming_global`, `advection_test`.

## Repository layout relevant to setup
- `src/` – Fortran modules (base, grid, fluids, IO, multigrid, gravity, particles, ...), `src/base/piernik.h`
  and `defines.c`.
- `problems/<name>/` – `piernik.def`, `initproblem.F90`, `problem.par`, optional `info`, `Makefile.in`,
  extra modules.
- `compilers/*.in` – compiler configs; `compilers/tests/` – feature test programs.
- `obj*/` – generated build directories, usually disposable. `runs/` contains run-specific parameters, logs, snapshots and restart checkpoints; preserve or back up needed runs before deleting them.
